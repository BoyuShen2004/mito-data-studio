# v1.1.1 guarded fresh-application reset

The reset is deliberately unavailable during normal serving. It preserves the
schema, migrations, one named superuser, deployment configuration and every
external source/reference byte. It clears business rows and app-owned content
under the dedicated `MITO_DATA_ROOT` only.

## Required gates

1. Create a root-only, non-zero PostgreSQL custom dump and data-root archive.
2. Verify the dump with `pg_restore -l`, list the archive, and record SHA-256.
3. Write the JSON verification marker with artifact paths, hashes and time.
4. Capture `reset_application_data` dry-run output and the storage manifest.
5. Drain writes and set `MITO_MAINTENANCE_MODE=true` plus the marker path. The
   maintenance middleware then rejects every new business mutation with 503;
   only authentication and the protected reset endpoints remain writable.
6. Restart privately and verify the deployment identity before issuing a token.

The CLI flow is:

```text
python manage.py reset_application_data
python manage.py reset_application_data --issue-confirmation \
  --phrase 'CLEAR ALL APPLICATION DATA' --admin admin
python manage.py reset_application_data --confirm '<single-use-token>' \
  --phrase 'CLEAR ALL APPLICATION DATA' --admin admin
```

The protected `/admin/settings` UI uses the same service. It additionally
requires the administrator's current password, CSRF token, exact phrase and a
server-created five-minute non-replayable token. Normal users cannot discover
or call the endpoints. Confirmation issuance is rate-limited.

After success, return `MITO_MAINTENANCE_MODE=false`, restart, verify empty
business counts, then perform a disposable create/edit/save/delete cycle.

Mock development login is independent. It is disabled by default and accepts
only `MOCK_DEV_LOGIN_ACCOUNTS` from server configuration. The frontend contains
neither passwords nor an arbitrary-username impersonation path.
